# Tapua'i — Fix → Test-Prep → Advance → Team-Test Roadmap

Companion to [LEGAL_BRIEFING.md](LEGAL_BRIEFING.md), [AUDIT_REPORT.md](AUDIT_REPORT.md), and [TEAMS.md](TEAMS.md#qa--ship-gate). This is the live tracker for closing the pre-launch security/compliance gaps, standing up real testing infrastructure, and running an internal test wave before any public beta. Update the status line under each phase as work lands — do not let this drift into a one-time snapshot.

## Context

Two audits found: (1) money/Aura/admin-data can currently be fabricated because RLS trusts the client instead of a verified payment; fixes are drafted but not yet applied to a live Supabase project. (2) The single biggest go-to-market risk is high-school NIL "pay-for-play" optics — Mālo is wired to a specific highlight clip (`reel_id` on `tips`), closer to "paying for a play" than the "gift to an athlete" framing the product needs. Separately, the repo had zero automated tests, no staging build pipeline, and no deployment target before this roadmap started.

Internal dogfooding runs now, in Stripe test mode, in parallel with Phase 1 — it is **not** gated on legal/compliance work. Only a public beta with real money is gated on Phase 1 + a written association position.

**Where things stand for testing, as of Round 33 (2026-09-22):** Phase 0's security work is done to the point that internal testing (Phase 3) is not blocked on it. Every table/RPC-fabrication bug found across 33 rounds is fixed, the admin login chain (four independent bugs, see Round 21) is fixed and verified live, and the two remaining "Hard Blocker" items below are explicitly scoped as *internal-testing-acceptable, public-beta-blocking* — meaning they do not need to close before Phase 3 testers get in, only before Phase 5. The two genuinely open items from this session (Round 23's payout balance ledger, Round 24's Stripe webhook wiring) are real product/feature decisions, not security holes blocking testing — payouts are simply disabled today (a stub, same as Phase 1 item 3 already notes), which is fine for testers who aren't expected to withdraw real money yet. **The actual bottleneck to getting testers in a real build is Phase 2**, which needs two things only the team can do (an Expo/EAS account, a throwaway staging Supabase project) — see Phase 2 below.

**Round 3 (2026-09-22, critical — found by a QA rotation, fixed same day):** `add_user_role` had **no role check at all** — any signed-in fan account (no anon key needed) could call it directly to set `is_admin = true` on their own profile, a full self-service privilege escalation that retroactively defeated every `current_user_role() = 'admin'` gate built this session. This is strictly worse than the Phase 5 "Hard blocker" above, since it doesn't need the anon key. Fixed: the RPC now only allows self-service `fan`/`athlete`; any other role (including `admin`) requires the caller to already be admin. Also closed a deeper hole the RPC fix alone wouldn't have caught — a raw `profiles` UPDATE could set `is_admin`/`role`/`roles` directly, bypassing the RPC entirely — via a new `before update` trigger (`guard_profiles_admin_escalation`) rejecting any admin-flag write from a non-admin session, as defense-in-depth alongside the RPC. Same pass also closed a related gap on `players`: `booster`/`operator` roles could still write `guardian_id` directly (bypassing `admin_set_player_guardian`, contradicting that fix's own documentation) — now column-grant-restricted, with two new narrow RPCs (`parent_set_player_consent`, `admin_approve_player_consent`) replacing the two legitimate direct-write call sites that would otherwise have broken.

**Round 5 (2026-09-22): self-directed sweep — Storage layer, and completing round 3's fix.** Storage bucket policies (`reels`/`game_highlights`/`avatars`) required no authentication at all for upload/update — anyone with the anon key could write arbitrary files to public buckets, a real moderation concern for an app hosting minors' video. Fixed: all INSERT/UPDATE now require a real session; reads stay public. Separately, found round 3's admin-escalation fix was incomplete: the defense-in-depth trigger only covered `UPDATE`, and `"Users insert own profile"` still had the `auth.role() = 'anon'` bypass — meaning a fresh `profiles` row could still be INSERTed with `is_admin = true`, skipping both the RPC fix and the trigger. Confirmed the live exploit window was narrower than it looked (a unique FK to `auth.users(id)` means an attacker needs a real, existing auth account with no profile row yet — not "grab any account"), but fixed properly regardless: the anon branch is gone from the INSERT policy, and the trigger now covers `before insert or update`. Also found and fixed `subscriber_requests` (the Vault "Direct Request" fan→athlete messages) — this stores actual message text, and both read and insert were fully public (`using (true)`/`with check (true)`); now scoped to sender, receiving athlete, or admin.

**Round 4 (2026-09-22): systematic sweep of every `SECURITY DEFINER` function taking a `target_*` parameter, same day as round 3.** Confirmed real: `get_fan_tip_history` fell back to trusting a client-supplied `fan_user_id` whenever there was no session (`coalesce(auth.uid(), fan_user_id)`) and was anon-executable — anyone with the public anon key could read any fan's complete Mālo tipping history with no login, by guessing an id (easy, since `profiles` is already publicly readable — a separate, already-deferred gap). Fixed: always requires a real session, `authenticated`-only now. Confirmed this exact `coalesce(auth.uid(), ...)` shape does not appear anywhere else in the schema. Also found and fixed: `can_confirm_player_tag` had an explicit `auth.role() = 'anon' or ...` bypass, meaning anyone with the anon key — no session — could confirm or reject the athlete tag on any Highlight, which feeds directly into Player-of-the-Week/Spotlight scoring (a competition-fairness issue, not just data exposure); and `set_player_vault_locked` had no ownership check at all, letting any signed-in fan lock or unlock any athlete's Vault. Both fixed with proper role/ownership checks. Full one-line-per-function inventory of ~20 functions is in that task's transcript — two more zero-check functions were found (`delete_sport_config`, `triage_app_feedback`) but both are masked by, and deferred alongside, the Phase 5 "Hard blocker" above (same root cause: no real session backing Studio Unlock).

**Round 6 (2026-09-22): swept a class of bug none of rounds 2-5 covered — Realtime Broadcast, not table RLS.** `useGameEventBroadcast.ts` (live on every Reel via `ReelCard.tsx`) and `sendGameEventBroadcast` (`lib/operator.ts`, not yet wired to a UI button but fully reachable directly against the project) push/receive live sideline callouts over a Supabase Realtime Broadcast channel named `game_events_{gameId}`. Broadcast messages are not table writes, so none of the `game_events` table's RLS policies ever applied to them — with no Realtime Authorization configured, anyone holding the app's public anon key (baked into the client bundle, not a secret) could open a WebSocket directly, join any game's topic, and broadcast a fabricated "Touchdown"/arbitrary-text event that would render live on every fan's screen watching that game, with zero authentication and no rate limit — entirely independent of whether the app's own UI calls the sender function. Fixed: both channel() calls now pass `{ private: true }`, and new `realtime.messages` RLS policies (schema.sql) gate send to operator/admin (or anon while the game is still unclaimed, mirroring the existing `game_events` INSERT policy) while keeping receive open to every fan. This is a distinct vulnerability class from everything found in rounds 2-5 (Broadcast/Presence vs. table RLS) — worth checking on every future Realtime channel added to the app, not just table policies. Also noted, lower severity, not fixed this round: `increment_reel_tips` (a reel's *displayed* Mālo total, not the money ledger — real payouts read `tips` directly, confirmed via `lib/reels.ts` comment) has no per-call upper bound at all, unlike `add_user_aura`'s documented 5000-point stopgap cap — a single call could set an obviously-fake total instantly. Same "client-fabricatable vanity counter, real money unaffected" class already accepted for Aura; worth capping for consistency in a future pass but not a money or data-integrity issue on its own.

**Round 7 (2026-09-22, critical — the paywall itself, not a data-fabrication bug): the Vault / Exclusive / Flash-Unlock paywall was never enforced by the database.** `"Public read reels" using (true)` plus `grant select on reels to anon, authenticated` meant any client holding the app's public anon key could read `video_url` for every reel — including Vault-only and subscriber-Exclusive clips — via a raw REST call, with no subscription, no Vault unlock, not even a login. Every `.eq('is_vault_only', false)` filter in `lib/reels.ts` was a feed convenience, not an access boundary; `useAthleteSubscription.ts` only ever gated the client's own render decision. This is a different class of bug from rounds 2-6 (fabricating data) — it's the actual paid-content product being bypassable by anyone. Fixed with user sign-off on approach (view over waiting for the Mux/Cloudflare decision, since it's available now and independent of that migration): base-table SELECT on `reels` is narrowed to the uploader's own row or an admin; a new `public.reels_feed` view is the one real fan-facing read path, returning every column unchanged except `video_url`, which comes back as `''` unless the row is unlocked, Flash-Unlocked right now, or the caller is the uploader / an admin / an active subscriber to the tagged athlete (checked against `subscriptions`). `lib/reels.ts` and `lib/spotlight.ts` (the only two call sites reading someone else's `video_url`) now read the view; `lib/admin.ts` / `lib/adminCatalog.ts` (metadata-only) and `MediaUploadService.ts` (insert-then-read-own-row) keep reading the base table, matching the narrower policy. Full details, including why the view intentionally is not `security_invoker`, in `docs/SCHEMA.md`'s `reels` section. **Verified 2026-09-22, live:** `lib/reels.ts`'s `players (...)` nested embed through `reels_feed` resolves correctly against the real Supabase/PostgREST instance (schema.sql applied — see Round 8) — tapping an athlete's name from a Highlight loads their profile as expected, which was broken (stuck on "Loading athlete...") for the few hours between landing this fix in the repo and actually applying it to the live project.

**Round 11 (2026-09-22): two genuine findings, both fixed — neither in the already-accepted Studio Unlock/Operator blocker class.** (1) `crew_follows` (`for all`) and `crew_push_queue` (SELECT) both had an unconditional `auth.role() = 'anon' or ...` bypass — but unlike the 8 tables in the Phase 5 hard blocker, this is a plain fan feature gated by Soft-Wall sign-in, not an admin/operator desk with the "no real session" excuse, so there was no legitimate anon caller at all: `toggle_crew_follow` (SECURITY DEFINER) already required `auth.uid()`, and the client's direct-table fallback in `lib/crew.ts` always writes the caller's own id. **Round 12 (2026-09-22), critical — arguably the most severe finding of this whole sweep: Varsity verification codes were hardcoded in plain text in a file committed to git.** `redeem_team_code` is the real, live production mechanism behind "⚡ VERIFIED VARSITY" (`VerifyAthleteModal.tsx`) — a coach hands an athlete a code, they type it in, and they instantly get school-claimed, athlete-roled, Varsity-verified status with zero staff approval, by design (fast onboarding). `schema.sql` and `supabase/athlete_verification.sql` both hardcoded every seed school's actual code in plain text (`WSTLK-2026`, `LPKHS-2026`, ...) — and those seed schools are real Utah high schools (Westlake, Lone Peak, American Fork, Timpview), the actual Phase 5 GTM target, not placeholder names. Anyone with any access to this repository's history already has every one of those codes, permanently — rotating them doesn't erase the git history exposure, only stops it from mattering going forward. Separately, and independent of the leak: the code *format* itself (`SCHOOL-SPORT-YEAR`, from a small fixed set of school abbreviations and ~12 sport tokens) is small enough to brute-force directly through `redeem_team_code` even if it had never been committed anywhere — the RPC has no rate limit. Fixed the immediate hygiene issue: both files no longer hardcode any school's code; a comment documents the correct process (generate high-entropy codes out-of-band, set via the SQL Editor directly, hand to the coach out-of-band — never in a committed file). **Resolved same day:** user chose to rotate (new random codes handed over in chat directly, not committed — run once via the SQL Editor) and to add a rate limit rather than move to fully high-entropy codes. Rate limit implemented in both `schema.sql` and `supabase/athlete_verification.sql`: `profiles.team_code_fail_count` / `team_code_locked_until`, 5 wrong guesses locks an account out of `redeem_team_code` for 15 minutes, checked before the code lookup runs (a locked-out account can't keep probing), a correct code resets the counter. **Why this matters for the end goal:** this is exactly a Phase 0 item that must close before Phase 5 — the entire NIL/trust model this product is built on rests on "verified Varsity" actually meaning something; today it means "read this git repo."

**Round 13 (2026-09-22), critical — the Round 12 fix was necessary but not sufficient; the real hole was structural.** Rotating the leaked codes and rate-limiting `redeem_team_code` doesn't help if the code is readable another way, and it was: `schools_and_teams` has always had `grant select on ... to anon, authenticated` with a public `using (true)` policy — meaning `team_code` was (and, on your live project until this fix ships, still is) readable directly via a plain `select team_code from schools_and_teams` REST call, completely bypassing the RPC and its new lockout. Worse: `search_schools_and_teams` (SECURITY DEFINER, `select s.*`, callable by `anon`) returned the full row including `team_code` to anyone searching for a school, in both `schema.sql` and the standalone `supabase/schools_and_teams.sql` (which also had its own copy of the original hardcoded-codes bug from Round 12, missed in that pass). Worst of all: `data/verification.ts` shipped a `DEMO_TEAM_CODES` map hardcoding every real school's code *inside the app bundle itself* — extractable from any installed copy of the app by unpacking the JS bundle, no git access needed at all — and it was live as a fallback in `redeemTeamCode()` that could grant real `profiles.is_verified = true`, reachable whenever the RPC call failed for any reason (including a transient schema-cache lag after a function signature change — exactly what Round 12's own fix just did). Fixed: `schools_and_teams` SELECT is now a column-level grant excluding `team_code` (with an explicit `REVOKE` first, since GRANT is additive — a narrower grant on top of the old blanket one would have been a silent no-op on your already-live project); `search_schools_and_teams` now explicitly enumerates safe columns in both files; `redeemTeamCode()`'s two fallback branches (direct table filter, `DEMO_TEAM_CODES`) are removed entirely, and `DEMO_TEAM_CODES` itself is deleted from the codebase — the RPC is the only path now, any failure surfaces as an error rather than silently degrading. **Every one of these needs schema.sql re-applied** (the column-grant fix and the `search_schools_and_teams` fix are both there) **on top of Round 12's rotation** for the fix to actually take effect.

**Round 15 (2026-09-22), critical — a role-escalation bug on the same scale as Round 3's, found by finally sweeping the Parent/Booster/Sponsor portals (untouched all session).** `add_user_role` already refuses to self-grant `booster`/`operator`/`parent`/`sponsor`/`admin` unless the caller is already admin (Round 3). But `guard_profiles_admin_escalation` — the trigger that's supposed to close the matching raw-`UPDATE`-on-`profiles` bypass — only ever checked for `is_admin`/`role = 'admin'`, never the other four. Combined with `profiles`'s blanket `grant ... update` (no column restriction): any signed-in fan could run `update profiles set role = 'booster' where user_id = auth.uid()` directly and instantly pass `current_user_role() in ('booster', 'admin', 'operator')` — unlocking full `players` table write access ("Staff write players" — insert/update any athlete's roster, jersey numbers, etc.) and every other booster/operator-gated policy found throughout this sweep, with zero admin grant. Found while reviewing `app/(booster)/booster/index.tsx`'s raw `players`/`verification_requests` writes — those turned out to be properly RLS-gated on their own, which is what surfaced that the *real* gate (`current_user_role()`) was itself forgeable. Fixed: generalized the trigger to check each of the 5 privileged roles individually (not a coarse "privileged vs not" boolean, which would have let someone holding one legitimate privileged role self-upgrade to another) — a role newly present after the write that wasn't there before is rejected unless the caller is already admin. Also noted, not a security issue: Parent HQ's "Linked student-athletes" list is unfiltered (`useRoster()` returns the full public roster), a UI/UX bug worth a separate cleanup pass — the actual consent-toggle RPC already re-validates `guardian_id` ownership server-side regardless of what the screen displays.

**Second hard blocker found 2026-09-22 (Round 9 security sweep), explicitly accepted as an internal-testing-only risk, NOT to ship publicly with:** the Round 7 paywall fix (nulling `video_url` in `reels_feed` for Vault-only/Exclusive clips the caller isn't entitled to) only closed the *database* read path. The actual video files are unaffected: `reels`/`game_highlights`/`avatars` are all `public = true` Storage buckets with a read policy of `using (bucket_id = '...')` — no auth check — which means (a) a public bucket serves files over an unauthenticated URL that bypasses `storage.objects` RLS for direct GETs entirely, and (b) that same open RLS also governs the bucket's list endpoint, so every filename can be enumerated with no login at all. Upload paths (`MediaUploadService.ts`) are `reels/{owner}/{Date.now()}.mp4` — `owner` is the uploader's raw auth user id, itself independently discoverable since `profiles` (including `profiles.user_id`) is fully public. Net effect: any Vault-locked/Exclusive clip's video file can be listed and downloaded directly from Storage, completely bypassing the `reels_feed` entitlement check. **Real fix (not yet built, a product decision, explicitly not defaulted on):** locked content needs to move to a private bucket served only via entitlement-checked, short-lived signed URLs (an RPC reusing `reels_feed`'s CASE logic) — a real feature, not an RLS tweak, and effectively subsumed by whichever of Mux/Cloudflare Stream gets picked (both give private/signed playback natively) — user explicitly chose to defer fixing this until that video-host decision lands, same treatment as the Studio Unlock blocker below, to avoid building Storage-specific code that gets thrown away on migration. Do not close Phase 5 without resolving this.

**First hard blocker found 2026-09-22, explicitly accepted as an internal-testing-only risk, NOT to ship publicly with:** `current_user_role()` only resolves to `'admin'` for a real Supabase-authenticated session — but the Expo `/admin` app's "Studio Unlock" is a purely client-side cosmetic gate with no server-side session behind it, and the Operator PIN-claim flow has the same shape (no real Supabase session). Because of this, 8+ tables' "admin-only" or "operator-only" RLS policies actually read `auth.role() = 'anon' or current_user_role() = 'admin'` — which is satisfied by *anyone* holding the public anon key, not just a Studio-unlocked admin or PIN-claimed operator: `operator_gigs`, `operator_checkins` (this one has no role check at all — `using (true)`), `shop_products`, `schools_and_teams`, `cheer_polls`, `sponsorships` (UPDATE/DELETE only — INSERT already fixed), `app_feedback` (read AND write — any fan's feedback is readable/editable by anyone), `wishlist_items`, `sport_configs`. The anon key ships inside the app bundle, so this is invisible risk today (small trusted internal testers) and a real one the moment the app is public. **Real fix (not yet built, a product decision, explicitly not defaulted on):** Studio Unlock and/or the Operator PIN flow need to establish a real Supabase session (or an equivalent server-verifiable credential) so `current_user_role()` can actually distinguish an admin/operator from anyone else — only after that can the `auth.role() = 'anon' or ...` bypass be safely dropped from all of these policies. Do not close Phase 5 without resolving this.
