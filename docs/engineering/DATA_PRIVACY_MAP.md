# Tapua'i — Data collection map & recommended structure

**Status:** Internal engineering reference, not legal advice, not a Privacy Policy, and not a claim of compliance with any statute. It exists so counsel drafting the real Privacy Policy (`docs/company/COMPANY_PHASES.md` §L4 item 2) has an accurate starting inventory instead of reconstructing one from the schema by hand, and so this repo has one place to re-check whenever a new table, column, or RPC starts collecting something about a real person.

Read with [LEGAL_BRIEFING.md](../legal/LEGAL_BRIEFING.md) (the issue map — COPPA, minors-as-payees, money transmitter, school footage) and [COMPANY_PHASES.md](../company/COMPANY_PHASES.md) (when the real Privacy Policy actually gets drafted, by counsel). This file answers "what do we actually collect today" so that conversation starts from fact, not guesswork.

## 1. What we collect, by category

| Category | Where (table / service) | Subject | Notes |
| --- | --- | --- | --- |
| Identity (name, username, avatar, bio, social handles) | `profiles` | Any signed-in user | `bio`/`social_links` are self-authored, hideable per-field (`profile_visibility`) from other *users*, but the base `profiles` row is still publicly `SELECT`-able at the database layer (see §3). |
| Athlete roster identity (real name, jersey, school, physical measurables) | `players` | **Minors**, usually entered by an operator/admin, not the athlete | No sign-in or attestation required for a `players` row to exist — a minor can be named on the roster with zero account of their own. Publicly `SELECT`-able by design (fans browse rosters). |
| Athlete performance data | `athlete_career_stats`, `athlete_game_logs` | Minors | Tied to `player_id`; same public-read posture as `players`. |
| Video content | `reels` (`video_url`, `uploaded_by`, `player_id`) | Minors (subject), any signed-in user (uploader) | Free Highlights sit in a bucket with a public URL; Vault/Exclusive clips use a private bucket + short-lived signed URL (`reel_vault`, `resolvePlaybackUrl`). Video uploads have no EXIF/metadata stripping — see §3.3 (photo stories are the exception, next row). |
| Photo stories (photos + per-photo descriptions) — *new 2026-10-07, SQL not applied* | `reel_photos` (`image_path` (Storage path, not a URL), `description` ≤ 200 chars, `width`, `height`, `position`), `reels.media_type = 'photo_story'` / `photo_count`; public read through `reel_photos_feed` and `reels_feed.cover_path`; Storage `reels/{uploader uid}/stories/{reel id}/{position}-{timestamp}.jpg` | Minors (tagged athlete **and untagged people in the photo**), uploader | 1–10 photos per story, written only by RPC `set_reel_photos` (owner's own Storage folder, reel not removed). Base-table SELECT is uploader/admin; everyone else reads the view, which drops removed reels and gates `image_path` like `video_url`. **Bucket `reels` is public** — anyone with a URL can open a photo, and v1 offers no Vault photos for that reason. Descriptions are free text and can contain names or places. **Metadata rule:** location/camera data is removed before upload (see §3.3); not yet checked on real devices. Removing a story cascades the rows; the image files in Storage are not deleted by that cascade. Design: `design/PHOTO_STORIES_DESIGN.md`; legal: LEGAL_BRIEFING rows U, V. |
| Financial / payment records | `tips`, `subscriptions`, `sponsorships`, `disbursements`, `shop_orders` | Payer (any age) + minor recipient | Amounts, timestamps, and (for `tips`) *why* a gift happened (`origin`/`entry`/`source_label`). No card data ever touches the app's own tables — that stays with Stripe. |
| Location | `operator_checkins` (`latitude`, `longitude`) | Field operator (adult, in practice) | Collected once per gig check-in via `expo-location`, persisted indefinitely, no purge job. See §3 for the RLS gap fixed alongside this doc. |
| Behavioral / engagement | `reel_hype_votes`, `saved_reels`, `crew_follows`, `crew_push_queue`, `telemetry_logs`, `app_feedback` | Any signed-in user (and, for `telemetry_logs`/`app_feedback`, sometimes anonymous) | `telemetry_logs` rows are not foreign-keyed to a user id, and guests (no account) can insert them on purpose (browse-first). Row shape is bounded by CHECKs (`20260929190000_telemetry_logs_bounds.sql`, applied to staging): known event types, capped durations, text and payload sizes. Many small valid-looking rows are still possible; per-user logging is an open owner decision (`docs/STATE.md` §6 item 1) and needs Terms copy first. |
| Consent / age state | `profiles.age_confirmed_13_plus`, `players.parental_consent_approved` / `guardian_consent_at` | Minors (subject), parent (actor) | Sign-up collects a self-attested 13+ boolean. Custodial setup separately collects exact athlete DOB in `athlete_birthdates`; see the next row and §4. |
| Custodial identity and approvals | `athlete_birthdates`, `custodial_accounts`, `custodial_withdrawals` | Athlete + linked guardian | Guardian supplies `birth_date` for handover calculations (`guardian_setup_custodial`); `entered_by`/time, guardian link, Stripe account reference, bank-name attestation, withdrawal amount/note and decision are retained. DOB table is separated from public rosters; `custodial_role` gates SELECT to linked guardian, verified athlete or admin. Exact retention and correction procedure need scoping. September SQL is recorded applied to staging only. |
| Verification and school contact | `verification_requests`, `school_confirmers`, `athlete_vouches` | Athlete/requester, school AD/coach, teammates | Claim sport/class/jersey, school contact name/email, token hash and expiry, hashed meeting code/attempts, confirmer identity/decision notes, and teammate-vouch links. School confirmer reads are admin-only; verification request and vouch access must be covered in the export/retention review. |
| Account mentions and content reports | `reel_account_tags`, `reel_reports`, `reels.attested_at` / `rights_version` | Tagged account, uploader, reporter, filmed athlete | Mentions retain profile/clip links, confirmation status and timestamps; confirmed tags are public, pending tags limited to tagged account/uploader via policies and RPCs. Reports retain reporter UUID, reason and time with admin-only SELECT. Account-tag SQL remains unapplied; report SQL exists in canonical schema. |
| Rally and thank-you records | `rallies`, `donation_thanks` | Athlete, guardian, donor | Goal/story and approval state, donation links, preset thanks and optional clip references. Include these relationships when scoping account export or deletion. September SQL is recorded applied to staging only. |
| Device-local queue | `AsyncStorage` (`OfflineQueue`) | Any signed-in user | Can hold a `userId` plus pending Aura/vote/bookmark/report actions unencrypted on-device until the next successful flush. |

## 2. Who we share data with

**Public sport identity (2026-10-07, prepared):** `profiles_public.athlete_sport` adds the selected sport only for linked athlete accounts, so public hero/Stats/Aura agree. Existing bio/social/stat visibility rules remain; no private numeric stats or financial fields are added. Migration `20261007211500_public_profile_sport.sql` is local and unapplied.

- **Stripe** — email (for Connect account contact), a Supabase-generated user id in metadata, and payment amounts. No name, DOB, or tax id is sent by this app's code (`createStripeAccount.ts`, `createPaymentIntent.ts`, `payouts.ts`). Stripe Connect Express accounts are built as **US individual** accounts — `LEGAL_BRIEFING.md` §5 already flags this as a likely mismatch for a 16-year-old payee; `COMPANY_PHASES.md` §B2 has the parent-as-payee redesign this needs before minors connect their own account.
- **Supabase Storage** — raw video, avatar and image bytes, uploaded verbatim with no metadata stripping, **except photo-story photos**, which are re-encoded and stripped of JPEG metadata first (§3.3). Supabase Auth also holds the sign-in email (password, magic link, or the Apple/Google token exchanged in `apps/mobile/src/frontend/lib/auth.ts`).
- **Apple** — Sign in with Apple requests email and full name, then the identity token is sent to Supabase Auth (`signInWithApple` in that file).
- **Google** — Google sign-in opens Google’s page through Supabase Auth (`signInWithGoogle` in that file).
- No analytics SDK, ad network, or data broker is listed in `apps/mobile/package.json` or `apps/admin-portal/package.json` (checked 2026-10-10). `apps/mobile/app.json` sets `updates.url` to Expo’s update service, and app source does not import `expo-updates`. This check did not confirm that address receives personal data.

## 3. Concrete gaps found (2026-09-28 audit; inventory corrected from local code 2026-10-07)

These are structural/engineering facts, not legal conclusions — counsel decides which ones are legally required to fix and on what timeline.

1. **Fixed in SQL, not yet applied:** `operator_checkins` (GPS coordinates) had a policy of `using (true) with check (true)` — no role check at all, weaker than its own sibling table `operator_gigs`. Any signed-in account, not just an operator, could read every check-in's location or write fabricated ones. `supabase/migrations/20261002120000_operator_checkins_role_check.sql` brings it to parity with `operator_gigs`'s existing (already-documented, already-accepted-for-internal-testing) anon/operator/admin check — see `docs/product/ROADMAP.md`'s Phase 5 "First hard blocker" note, which this now matches rather than falls short of. Not applied to any Supabase project yet.
2. **Not fixed, needs a product decision:** `profiles` and `players` both keep a blanket `using (true)` SELECT policy — the entire row, including `profiles.stripe_connect_id`, is publicly readable. This is the same gap `docs/product/ROADMAP.md` Phase 0 item 4 already tracks; the `profiles_public` view added for the bio/social-links feature (Round 34) does **not** close it. `players`' openness is a separate, more defensible case — school rosters are meant to be publicly browsable — but a minor's physical measurables (height/weight/40-yard time) being part of that public row is worth a specific counsel read.
3. **Partly fixed (photos only, 2026-10-07; device check pending):** photo-story photos are stripped before upload — picker `exif: false` and a re-encode, then `stripJpegMetadata` (`services/MediaUploadService.ts`) drops APP1–APP13, APP15, comment segments and anything after the image end (EXIF/GPS, XMP, IPTC, ICC, maker notes), keeping APP0, APP14 (colour) and the image data. A photo that is not a well-formed JPEG is refused rather than uploaded uncleaned. Unit tests cover the byte rules. **Gap:** nobody has yet confirmed on real iPhones and Android phones that no location survives and that orientation is still right after stripping (DEVICE_QA). **Still not fixed:** videos and avatars have no EXIF/location stripping — a camera-recorded Highlight can carry embedded GPS in its raw file, uploaded unmodified to a bucket with a public URL for free clips. Stripping video metadata is a bounded engineering task (re-encode or strip server-side, or client-side before upload) whenever it's prioritized.
4. **Not fixed, needs a product + legal decision:** no account-deletion or personal-data-export path exists in the app. Re-checked 2026-10-10: no account-export or account-deletion screen or RPC. Building this is a real feature, not a quick patch, because deletion has to decide what happens to rows a deleted user is linked to that other people depend on (a `tips` row an athlete's accounting relies on, a `players` row other fans follow, a `reels` row tagging someone else). A reasonable shape once scoped: soft-delete/anonymize `profiles` (null out `full_name`/`avatar_url`/`bio`, keep the row for FK integrity) rather than hard-delete, keep financial records (`tips`, `disbursements`) intact for the athlete's own accounting and any tax reporting, and let the requester see exactly what would be kept and why before confirming.
5. **Not fixed, already known:** `players` rows (a minor's name, school, physical stats) can exist with no linked `profiles`/auth account and no attestation of any kind — the 13+ checkbox on `profiles.age_confirmed_13_plus` never applies to a roster entry an operator or admin creates directly.
6. **Not fixed, already known and explicitly out of scope for engineering to build unprompted:** no CSAM/content-moderation vendor pipeline; current app has rights attestations, `reel_reports` reason records, role/threshold-based `reels.is_flagged`, and admin moderation — `docs/legal/LEGAL_BRIEFING.md` and `docs/company/COMPANY_PHASES.md` already say this is "a vendor plus a policy," not a schema change.

## 4. Recommended structure (for counsel to review, not a certification)

A product shape for counsel to review. This section does not say which statute applies, and it is not a certification:

1. **Data minimization, already partly in place** — sign-up uses a self-attested 13+ checkbox. Custodial setup collects exact athlete DOB separately to calculate handover age; this is an existing exception, not a new feature. Counsel and PRIVACY / CUSTODIAL must review necessity, access, correction and retention. Prefer booleans wherever they meet the product need.
2. **Separate the athlete's public identity from their account.** A `players` row is roster/public-identity data (name, school, jersey) that the product needs to be public for fans to find and follow. Personal *account* data (email, payment info, consent state) should stay behind the `profiles`/auth boundary it already does — the open item is narrowing what of `profiles` itself is public (§3.2), not making rosters private.
3. **Collect location only for the purpose stated, and only from the role that needs it.** `operator_checkins` is scoped correctly in *purpose* (a gig check-in) — item §3.1 closes the *access* gap; a retention limit (e.g., purge check-ins after a season) is a reasonable next step once a product owner decides how long that data is actually useful.
4. **A visible way to export what is held and to delete an account.** Neither path is built (§3.4). Counsel decides whether any statute requires them and what records must be kept. This file does not make that decision.
5. **Strip or avoid collecting metadata the product doesn't need.** EXIF/location in an uploaded video is a byproduct of the phone's camera, not something the product asks for — stripping it (§3.3) removes a category of personal data with no feature cost.
6. **Consent for a minor's data should be a real, re-checkable record, not a single boolean set once.** `players.parental_consent_approved` is already named in `docs/company/COMPANY_PHASES.md` §L4 item 3 as needing to become more than a boolean — this doc adds no new requirement there, just cites it as directly relevant to this same data-map exercise.

## 5. Keeping this current

Whenever a new table, column, Storage bucket, or RPC starts holding personal data about a real person, add a row to §1 here in the same pass — mirroring how `docs/product/ROADMAP.md`'s security sweep gets re-run when a new table/RPC/Realtime channel lands. This file and that one should stay siblings: one asks "can this be faked or stolen," the other asks "should we be holding this at all, and for how long."
