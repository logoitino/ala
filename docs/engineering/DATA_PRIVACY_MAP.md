# Tapua'i — Data collection map & recommended structure

**Status:** Internal engineering reference, not legal advice, not a Privacy Policy, and not a claim of compliance with any statute. It exists so counsel drafting the real Privacy Policy (`docs/company/COMPANY_PHASES.md` §L4 item 2) has an accurate starting inventory instead of reconstructing one from the schema by hand, and so this repo has one place to re-check whenever a new table, column, or RPC starts collecting something about a real person.

Read with [LEGAL_BRIEFING.md](../legal/LEGAL_BRIEFING.md) (the issue map — COPPA, minors-as-payees, money transmitter, school footage) and [COMPANY_PHASES.md](../company/COMPANY_PHASES.md) (when the real Privacy Policy actually gets drafted, by counsel). This file answers "what do we actually collect today" so that conversation starts from fact, not guesswork.

### Public game venues (LOCAL-02, 2026-10-21)

`games.venue`, `venue_school`, `venue_address` and `venue_notes` describe a public sporting
venue for one game. Admins enter/correct/clear them; guests and fans can read them with the
existing game row. They must not contain private homes, attendee whereabouts or operator GPS.
No fan location permission, tracking or new account/location identifier is collected. Venue
information follows existing game retention; no new timed retention process is created.

Get directions sends only the selected public address to Apple Maps (iOS) or Google Maps
(Android/web) on an explicit tap; the provider applies its own location/privacy choices.
Tapua'i does not read that provider's location or route. Existing telemetry may record only
fixed `local_directions` / `local_directions_open_failed` event codes with surface `local`,
never game identity, school/address/note, destination URL or raw provider exception. A tap
records intent, not navigation success or attendance. Hosted delivery/consent remains governed
by existing telemetry rules. Written venue SQL is not hosted activation; see [LOCAL-02](../agents/LOCAL-02.md).

### Telemetry delivery and local health (HEALTH-01)

The 2026-10-13 local repair keeps the existing `TelemetryEvent` / `track*` API and
`telemetry_logs` row fields, database permissions and guest insertion posture unchanged.
`TelemetryManager` still sends supplied `video_id`, `channel`, `step`, durations, attempts and
`payload: Record<string, unknown>`; it does not redact or inspect personal contents in that
payload. Existing SQL CHECKs bound types/text/payload size on the database that has them applied,
not consent or semantic safety. Source owners must avoid personal/private contents under the
[safe-log contract](ENGINEERING_SUPPORT.md#pairing-and-safe-logs). No privacy certification is
established by this delivery repair.

The client holds at most 120 queued-plus-active row reservations and sends batches of at most
15 with a ten-second caller timeout. This bounds row count, not per-row payload bytes. Timed-out
or otherwise uncertain INSERTs are counted and never replayed; they may have committed remotely.
An abort-ignoring request can retain its attempted raw payload until HTTP settlement and blocks
new sends in that instance. The ordinary queue is memory-only; it does not become an encrypted
or durable store. Disposal discards queued rows and requests abort; process exit/singleton
reset loses the local history. `getInstance()` keeps a disposed singleton inert; it does not
automatically replace it while an older transport could still be unresolved.

`getHealth(): TelemetryHealthSnapshot` exposes only frozen counters, fixed phase/failure codes,
capacity/batch/timeout values and local success/failure timestamps. It exposes no event bodies,
queued rows, identifiers, credentials or raw provider error. This diagnostic is process-local,
not a new persisted telemetry table or personal-data export. The existing QA desk samples it
on focus/refresh and after offline replay, recording the local sample time; telemetry digest and
OfflineQueue reads keep separate error/unread states. Two fixed global slots retain only a
pending flag per source across refresh/focus/remount/development reload: no response body,
actor identity or previous result is cached/reused there. A ten-second UI timeout does not
cancel the underlying read or release its slot; only actual settlement does. Old results remain
with their original caller and cannot populate a later generation. Repair writes retain their
locks and show unconfirmed status until actual settlement, without timeout replay. These
controls add no persisted collection or change to existing event payload access. Its counters/timestamps are not
proof of hosted retention, fleet coverage, consent or durable crash recovery. See
[HEALTH-01](../agents/HEALTH-01.md) for actual local checks and DATA_GOVERNANCE's export/reader
impact review. TELEMETRY/BACKEND retain hosted-delivery work; PRIVACY_ENGINEERING and the
owner/counsel retain payload, access, consent and retention decisions.

## 2. Who we share data with

**Public sport identity (2026-10-07, prepared):** `profiles_public.athlete_sport` adds the selected sport only for linked athlete accounts, so public hero/Stats/Aura agree. Existing bio/social/stat visibility rules remain; no private numeric stats or financial fields are added. Migration `20261007211500_public_profile_sport.sql` is local and unapplied.

- **Stripe** — email (for Connect account contact), a Supabase-generated user id in metadata, and payment amounts. No name, DOB, or tax id is sent by this app's code (`createStripeAccount.ts`, `createPaymentIntent.ts`, `payouts.ts`). Stripe Connect Express accounts are built as **US individual** accounts — `LEGAL_BRIEFING.md` §5 already flags this as a likely mismatch for a 16-year-old payee; `COMPANY_PHASES.md` §B2 has the parent-as-payee redesign this needs before minors connect their own account.
- **Supabase Storage** — raw video, avatar and image bytes, uploaded verbatim with no metadata stripping, **except photo-story photos**, which are re-encoded and stripped of JPEG metadata first (§3.3). Supabase Auth also holds the sign-in email (password, magic link, or the Apple/Google token exchanged in `apps/mobile/src/frontend/lib/auth.ts`).
- **Apple** — Sign in with Apple requests email and full name, then the identity token is sent to Supabase Auth (`signInWithApple` in that file).
- **Google** — Google sign-in opens Google’s page through Supabase Auth (`signInWithGoogle` in that file).
- No analytics SDK, ad network, or data broker is listed in `apps/mobile/package.json` or `apps/admin-portal/package.json` (checked 2026-10-10). `apps/mobile/app.json` sets `updates.url` to Expo’s update service, and app source does not import `expo-updates`. This check did not confirm that address receives personal data.

## 3. Concrete gaps found (2026-09-28 audit; inventory corrected from local code 2026-10-07)

These are structural/engineering facts, not legal conclusions — counsel decides which ones are legally required to fix and on what timeline.

1. **Fixed in SQL, not yet applied:** `operator_checkins` (GPS coordinates) had a policy of `using (true) with check (true)` — no role check at all, weaker than its own sibling table `operator_gigs`. Any signed-in account, not just an operator, could read every check-in's location or write fabricated ones. `supabase/migrations/20261002120000_operator_checkins_role_check.sql` brings it to parity with `operator_gigs`'s existing (already-documented, already-accepted-for-internal-testing) anon/operator/admin check — see `docs/product/ROADMAP.md`'s Phase 5 "First hard blocker" note, which this now matches rather than falls short of. Not applied to any Supabase project yet.
2. **Not fixed, needs a product decision:** `profiles` and `players` both keep a blanket `using (true)` SELECT policy — the entire row, including `profiles.stripe_connect_id`, is publicly readable. This is the same gap `docs/product/ROADMAP.md` Phase 0 item 4 already tracks; the `profiles_public` view added for the bio/social-links feature (Round 34) does **not** close it. `players`' openness is a separate, more defensible case — school rosters are meant to be publicly browsable — but a minor's physical measurables (height/weight/40-yard time) being part of that public row is worth a specific counsel read.
3. **Partly fixed (photos only, 2026-10-07; device check pending):** photo-story photos are stripped before upload — picker `exif: false`, native JPEG re-encoding when available, then `stripJpegMetadata` (`services/MediaUploadService.ts`) drops original APP1–APP13, APP15, comment segments and anything after the image end (EXIF/GPS, camera data, XMP, IPTC, ICC, maker notes), keeping APP0, APP14 (colour) and the image data. If the original EXIF Orientation is not 1, the cleaner writes a minimal APP1 containing only that orientation tag; GPS and camera fields are not retained. A photo that is not a well-formed JPEG is refused rather than uploaded uncleaned. Existing `MediaUploadService.test.ts` cases cover the byte rules, including orientation-only APP1 output. **Gap:** nobody has yet confirmed on real iPhones and Android phones that no location survives and that orientation is still right after stripping (DEVICE_QA). **Still not fixed:** videos and avatars have no EXIF/location stripping — a camera-recorded Highlight can carry embedded GPS in its raw file, uploaded unmodified to a bucket with a public URL for free clips. Stripping video metadata is a bounded engineering task (re-encode or strip server-side, or client-side before upload) whenever it's prioritized.
4. **Not fixed, needs a product + legal decision:** no account-deletion or personal-data-export path exists in the app. Re-checked 2026-10-10: no account-export or account-deletion screen or RPC. Building this is a real feature, not a quick patch, because deletion has to decide what happens to rows a deleted user is linked to that other people depend on (a `tips` row an athlete's accounting relies on, a `players` row other fans follow, a `reels` row tagging someone else). A reasonable shape once scoped: soft-delete/anonymize `profiles` (null out `full_name`/`avatar_url`/`bio`, keep the row for FK integrity) rather than hard-delete, keep financial records (`tips`, `disbursements`) intact for the athlete's own accounting and any tax reporting, and let the requester see exactly what would be kept and why before confirming.
5. **Not fixed, already known:** `players` rows (a minor's name, school, physical stats) can exist with no linked `profiles`/auth account and no attestation of any kind — the 13+ checkbox on `profiles.age_confirmed_13_plus` never applies to a roster entry an operator or admin creates directly.
6. **Not fixed, already known and explicitly out of scope for engineering to build unprompted:** no CSAM/content-moderation vendor pipeline; current app has rights attestations, `reel_reports` reason records, role/threshold-based `reels.is_flagged`, and admin moderation — `docs/legal/LEGAL_BRIEFING.md` and `docs/company/COMPANY_PHASES.md` already say this is "a vendor plus a policy," not a schema change.

## 4. Recommended structure (for counsel to review, not a certification)

A product shape for counsel to review. This section does not say which statute applies, and it is not a certification:

1. **Data minimization, current MINOR-01 source** — sign-up uses birth month and year; unknown age denies restricted actions and under-13 is refused/closed. This replaces the earlier self-attested 13+ checkbox; the age claim and guardian link are not independent identity or legal-guardianship proof. Custodial setup collects exact athlete DOB separately to calculate handover age; this is an existing exception, not a new feature. Counsel and PRIVACY / CUSTODIAL must review necessity, access, correction and retention. Prefer booleans wherever they meet the product need.
2. **Separate the athlete's public identity from their account.** A `players` row is roster/public-identity data (name, school, jersey) that the product needs to be public for fans to find and follow. Personal *account* data (email, payment info, consent state) should stay behind the `profiles`/auth boundary it already does — the open item is narrowing what of `profiles` itself is public (§3.2), not making rosters private.
3. **Collect location only for the purpose stated, and only from the role that needs it.** `operator_checkins` is scoped correctly in *purpose* (a gig check-in) — item §3.1 closes the *access* gap; a retention limit (e.g., purge check-ins after a season) is a reasonable next step once a product owner decides how long that data is actually useful. **2026-10-13 (DATA-01-F3):** the master data map shows nothing in the app reads `operator_checkins` at all, so the location is collected with no use yet; OPERATOR and PRIVACY_ENGINEERING decide between a reader with a retention limit and not collecting it ([DATA_GOVERNANCE.md](DATA_GOVERNANCE.md)). **Closed locally the same day:** the Live games desk reads check-ins only through `admin_list_operator_checkins`, which rounds location to two decimals (about 1 km), Direct table reads are closed for every client (insert-only policy). **PRIVACY_ENGINEERING decided 2026-10-13: 30 days, automatic.** The check-in has no current purpose (paid gigs are Wave 3) and operators may be minors, so the database stores location already rounded to two decimals, sets the time itself (a client-sent future date could otherwise dodge expiry), and deletes check-ins older than 30 days on every insert and every admin read through one function, `expire_operator_checkins`; `admin_purge_operator_checkins` clears sooner (minimum 7). Wave 3 should record a server-computed at-venue yes/no rather than coordinates. Migration `20261013120000` is written, not applied (replayed 46/46).
4. **A visible way to export what is held and to delete an account.** Neither path is built (§3.4). Counsel decides whether any statute requires them and what records must be kept. This file does not make that decision.
5. **Strip or avoid collecting metadata the product doesn't need.** EXIF/location in an uploaded video is a byproduct of the phone's camera, not something the product asks for — stripping it (§3.3) removes a category of personal data with no feature cost.
6. **Consent for a minor's data should be a real, re-checkable record, not a single boolean set once.** `players.parental_consent_approved` is already named in `docs/company/COMPANY_PHASES.md` §L4 item 3 as needing to become more than a boolean — this doc adds no new requirement there, just cites it as directly relevant to this same data-map exercise.
