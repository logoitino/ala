## Goal and baseline

A visitor should understand Tapua’i through the welcome and a short Highlights preview, then create an account or sign in to explore. An account is the first access condition; existing audience, block, minor-safety, role and paid-access rules remain independent conditions.

The pre-change [guest browsing helper](../../apps/mobile/src/frontend/data/guestBrowse.ts) limited Highlight plays to three without limiting profile movement. The [roster helper](../../apps/mobile/src/frontend/lib/roster.ts) reads individual players and the full roster; the prior canonical schema allowed public roster reads. The baseline [Auth context](../../apps/mobile/src/frontend/context/AuthContext.tsx) derived guest status from the absence of a session. The new migration/predicate and route boundary address the local baseline; hosted enforcement remains pending. These are source observations, not a test of the hosted database.

The selected approach is one small public preview with account checks before protected UI/data mounts, plus shared database restrictions and a narrow preview source. A dismissible popup by itself would leave direct URLs and data requests open. Removing every public entry would lose the approved welcome/preview journey.

## Access contract

| Visitor state | Allowed experience | Required behavior |
| --- | --- | --- |
| Signed out or anonymous-auth identity | Welcome, sign-in/account creation and at most three eligible public Highlight previews; required legal/auth recovery entry points | No full profile, search, roster/directory, other tab or account feature data. A fourth preview or protected destination requests an account. |
| Auth restoring or account eligibility unresolved | Loading/recovery UI | Do not mount protected children or start their reads while the decision is unresolved. A read failure is an unavailable state, not authorization. |
| Current signed-in, age-eligible account | Existing app destinations | Apply the original role, audience, block, minor and paid-access rules. An account must not unlock private or paid information by itself. |
| Signed out, replaced session or invalidated owner during a read/action | Public preview/recovery only | Unmount protected content and discard pending results and continuations from the outgoing lifetime. |

The same rules apply to desktop/tablet web, narrow web and native. Navigation controls and direct routes must agree. Review `/user/[id]`, `/athlete/[id]`, the legacy `/player/[id]`, Local directory/game paths and profile/gift/QR links, not only visible tab buttons. Authentication callbacks and required legal/recovery entry points must remain reachable without creating a redirect loop.

Blocked navigation explains why an account is needed and offers the existing sign-in/create flow. Successful sign-in resumes the intended destination only after current-session and required age checks complete. Cancel returns to the allowed preview without exposing the destination behind the account sheet. Repeated attempts must not stack account sheets. A URL or locally persisted role must never grant member access.

The [root Stack](../../apps/mobile/app/_layout.tsx) now applies [GuestAccessBoundary](../../apps/mobile/src/frontend/components/Auth/GuestAccessBoundary.tsx) through SDK 58 `screenLayout`, before each private screen child mounts or runs effects. Only the auth callback's own route descriptor grants its exemption; a globally active callback pathname does not exempt another retained screen. [AuthContext](../../apps/mobile/src/frontend/context/AuthContext.tsx) supplies fail-closed `accountReady` while profile setup is pending or failed, with retry/sign-out recovery. [WebAppShell](../../apps/mobile/src/frontend/components/Common/WebAppShell.tsx) and [SoftWallContext](../../apps/mobile/src/frontend/context/SoftWallContext.tsx) wait for account/profile and age readiness before rails or deferred actions resume.

[GuestHighlightsPreview](../../apps/mobile/src/frontend/components/Auth/GuestHighlightsPreview.tsx) replaces the full Home feed for guests. It provides the bounded clip window, Previous/Next, the account continuation and Terms/privacy without full-feed, roster, search or reaction hooks. There is no stored per-visitor quota or fingerprint: at most three clips belong to the current server preview window, which may change when eligible source content changes. The account continuation replaces a fourth clip.

## Source and security boundaries

The local [guest account migration](../../supabase/migrations/20261125180000_guest_account_access.sql) is appended identically to the [canonical schema](../../apps/mobile/src/backend/db/schema.sql). It revokes anon and inherited PUBLIC table/sequence/function privileges across non-extension public-schema objects, preserving existing effective privileges for `authenticated`, `service_role` and `supabase_auth_admin`. Anonymous access retains only `app_runtime_config` SELECT and calls to `current_user_role`, `account_browsing_allowed`, `enforce_registered_api_account` and `guest_highlights_preview`. Existing RLS tables receive an additional restrictive account SELECT condition (except runtime configuration); `get_public_profiles` also checks the registered-account predicate. The original authenticated row/role/privacy rules remain in place. Global PUBLIC function defaults are revoked for the migration owner, because a schema-only revoke would leave inherited execution available. Storage receives its own restrictive account policy for all operations; PostgREST pre-request hooks do not cover Storage requests.

`guest_highlights_preview()` is a separate bounded source over the privacy-filtered `reels_feed`: at most three free, nonremoved, unflagged video rows, with rights attestation/version and either no player tag or a confirmed tag on the actual raw reel. Raw pending/rejected tags are excluded even if a view suppresses the player identifier. Its DTO returns only `id`, `title`, `video_url` and `created_at`. It accepts no filters, ids, offset or caller-chosen limit. Private/exclusive media, photo sources and player/account lookup fields are not returned. Do not use a denied/missing preview RPC as permission to retry a broader table/view read.

The [shared policy](../../packages/shared-types/guestAccess.ts) owns the three-clip limit, preview DTO, registered-session check and route classification. Its current route rule permits `/` and `/auth/callback`; other destinations require an account. Required legal information must remain reachable through the permitted entry/auth experience without introducing a protected-data bypass.

[guestPreview](../../apps/mobile/src/frontend/lib/guestPreview.ts) validates the bounded four-field response and refuses widened, malformed or unavailable results. It uses the isolated sessionless client in [supabase.ts](../../apps/mobile/src/frontend/lib/supabase.ts), which cannot inherit persisted/anonymous-auth tokens. The same public client supplies published runtime reads through [runtime.ts](../../apps/mobile/src/frontend/lib/runtime.ts). Realtime is centralized in `runtime.subscribeAppRuntime`; [AppRuntimeContext](../../apps/mobile/src/frontend/context/AppRuntimeContext.tsx) consumes that adapter with zero direct SDK calls. Guest event payloads strip drafts, cleanup uses the originating client, and events after cleanup are discarded. The new regression passes in the final full check; source failures remain explicit.

The preview limit must come from that bounded response, not only a client counter that resets when a component remounts. A preview response or delayed member response must remain bound to its originating auth lifetime. Caller-supplied platform or role claims are not authority. `account_browsing_allowed()` requires a verified uid, a corresponding managed Auth user that is not anonymous, a nonanonymous JWT and existing age eligibility. Supabase anonymous-auth identities need denial tests even when they have an authenticated role and user id.

`enforce_registered_api_account()` is the API pre-request guard. It rejects missing/anonymous authenticated identity using both JWT and managed `auth.users.is_anonymous` state. The migration configures `authenticator`'s `pgrst.db_pre_request` and requests configuration reload when that role exists; standalone databases without it report that no hook was installed. Before changing grants it refuses an unrelated existing hook, including a database-specific blank override, rather than silently replacing an existing security control. Existing authenticated RPC privileges are preserved, so the installed API guard is required to prevent anonymous-auth callers from using other authenticated SECURITY DEFINER RPCs. Official Supabase API-security/changelog documentation was cached by the owner and read on 2026-11-25. **No hosted migration or API configuration has been applied or verified.** Local installation/refusal tests do not prove that hosted HTTP requests invoke the hook.

The [shared money-session helper](../../supabase/functions/_shared/money/session.ts) and [local API session adapter](../../apps/mobile/src/backend/api/session.ts) reject anonymous identities separately; a payment/API request does not gain account permission by supplying an anonymous uid. Corresponding Edge/local entry points are updated in source, with hosted Edge deployment still pending. Existing money authority and recipient/role rules remain independent.

The account policy is code-owned, with no permissive feature toggle. Existing [FeaturesTool](../../apps/mobile/src/frontend/components/Admin/FeaturesTool.tsx) at `/admin/features` reports the guest policy and source/install limitations. [Shared SOFT_WALL_GATES](../../packages/shared-types/index.ts), [adminCoverage](../../apps/mobile/src/frontend/lib/adminCoverage.ts), [expoDeskDirectory](../../packages/shared-types/admin/expoDeskDirectory.ts) and the [portal Auth report](../../apps/admin-portal/app/(protected)/auth/page.tsx) carry the same contract; Next remains read-only. No duplicate dashboard or anonymous-access toggle is added. Register the operational feature before app implementation and retain actual admin-ready then app-ready checkpoints under [FEATURE_ADMIN_WORKFLOW](FEATURE_ADMIN_WORKFLOW.md).

A source gate, passing local test or public-screen screenshot does not prove hosted denial.

Existing public Storage/media URLs may remain usable when somebody already knows a URL. Account gating is not media revocation, server rate limiting or comprehensive scraping protection. Those need their own source/provider work and evidence; do not claim them from this change.

## Acceptance and stop criteria

Use [the guest-access tester steps](TESTER_SCRIPT.md#guest-account-access--web-and-phone--2026-11-25) with the current source/build and separately with an authorized hosted environment.

Local acceptance requires tests of the bounded preview, protected-child/read suppression, direct-route denial, session restore/change/sign-out, age sequencing, sign-in resume/cancel and existing privacy/role controls. Backend tests must use real disposable PostgreSQL actors and direct table/view/RPC requests, not only UI mocks. Verify anon and anonymous-auth denials, legitimate account access, restricted identities and attempts to expand the preview. Record the commands, source hash, counts and failures in the feature's actual checkpoint evidence.

Stop or revise if a protected component loads before authorization, a cancellation exposes it, a denied preview falls back to broader data, an old session result reappears, a raw anonymous query returns protected records, or existing privacy/minor/role checks are weakened. Keep missing migrations, unverified runtime sensors, browser/device gaps and hosted apply/denial checks explicit. No conversion improvement or security completeness is inferred from local tests.
